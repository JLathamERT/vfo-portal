## 🔒 SECURITY INVARIANTS *(check on EVERY DB or handler change — these must NOT regress)*

Non-negotiables from the 2026-06-18 security remediation. Re-check any time you add a table, policy, handler, or function — do not let a new feature quietly undo these:

1. **Every new public table = RLS deny-all + verify.** Create it with `enable row level security` + `create policy "Deny all access" … for all to public using (false)` in the SAME migration, then confirm with an anon-key probe (`curl --head -H "apikey:<anon>" -H "Authorization:Bearer <anon>" -H "Prefer:count=exact" "<base>/rest/v1/<table>?select=*"` → must be `Content-Range: */0`). The anon key is PUBLIC and `anon`/`authenticated` hold full table grants, so RLS is the ONLY thing protecting the DB. (gotcha #141)
2. **Every member-facing AUTH handler = caller-ownership check on `auth.callerMemberNumber`, NEVER a body id.** The edge fn runs as service-role (bypasses RLS), so a handler that reads/writes by a body `client_id`/`ciq_id`/`enrollment_id` without re-checking ownership is an IDOR. Reuse `utils/client-ownership.ts` (`denyIfNotOwnClient`/`denyIfNotOwnEnrollment`) + `actions/ciq/shared.ts denyIfNotOwnCiq`. Role-gates are deny-by-OMISSION + matched by EXACT action name. (gotcha #142) **The same principle extends to every deny-by-default portal role whose allowlist is broad:** a `tax_planner` caller (2026-07-22) skips the tab + ADMIN_ONLY gates, so every planner-callable tax handler MUST also carry an in-handler `denyIfNotPlannerClient`/`denyIfNotPlannerPlan` GROUP-scope guard (`utils/tax-planner-ownership.ts`) — the allowlist alone is not an ownership check (gotcha #257). **Deny-by-OMISSION cuts both ways — an action in NO gate list is UNGATED, not safe:** `vault_upload_url` minted signed writes into any `member-vault`/`member-tax-returns` folder off a body `member_number` while sitting in no list at all, until it was added to `MEMBER_SCOPED_ACTIONS` on 2026-07-30. Every signed-upload-URL minter must be provably covered by a **named** confinement — either grep `role-gates.ts` and name the gate (gotcha #309), or, for a PUBLIC token page, show that the destination bucket + path are derived **entirely server-side from the token row** and that the request body selects nothing (`vault_tax_upload_url`, and the 2026-07-30 `vault_request_upload_url` whose `vault_upload_tokens` row is its whole credential — gotcha #310). A minter with neither is a hole.
3. **Every new SECURITY DEFINER function = pin `search_path` + `REVOKE EXECUTE … FROM public`.** (gotcha #143)
4. **After ANY DB/table/policy/function change → run the Supabase security advisor (`get_advisors`, type `security`) and confirm it's GREEN** — this is the automated net that catches a regressed (anon-reachable) table before it ships. It is part of the VERIFICATION GATE below.

Full audit history + live-verified detail: the 2026-06-18 security-remediation entry in [CHANGELOG.md](CHANGELOG.md) + gotchas #141–#146.

- **#252** — a revshare `share` is ALWAYS dollars of the TOTAL engagement; portion = `(share / totalGross) × paymentReceived`. Payout and display must use the same math.
- **#394** — the three legs are NOT prorated alike: MEMBER pays its entered share in full, STRATEGIC is gross-prorated, VFOS is the RESIDUAL. **Copy `contract-revshare.ts`; never re-derive from column names.** **#465** — a cell rendered as THE RESIDUAL launders every payee the component has never heard of into itself and still sums to its header, so **enumerate payees from the payout engine, never from the columns already rendered**; `Math.max(residual, 0)` then converts an over-booked row into a plausible `$0.00`, eating the one exact assertion that the parts agree with the whole. **#468(b) is its inverse and the pair is the test:** a residual that SWALLOWS a payee still sums to its header (a wrong breakdown with a right total), while an OMITTED payee under-sums and announces itself — the Payments table named three of Bitzer’s four legs and reached $1,215 of a $1,350 installment. So when a payout engine gains a leg, grep every surface that RENDERS the split, not only those that COMPUTE it, and assert legs === row total. Where several surfaces prorate the same money, one being right says nothing about the others — collapse them onto one helper that quotes the engine, fallback included, and prove a "legacy" branch dead with a census before porting it. **#466** — a SECOND WRITER reusing an existing type value conflates the two events permanently and every reader inherits it (`gc_add_credits` writes `"purchased"` for a comp): give a new writer its OWN value, and where you cannot, copy the test used by whichever total was already right — it will be keyed on a field the event itself produces (`amount_usd`, `stripe_session_id`), never on the type. Two lists in two repos that must agree are the same failure with a longer fuse, and an admin action with no `created_by` answers no questions later.
- **#304** — `member_contribution` is a member-funded DISCOUNT and Member Share is entered ALREADY NET of it — never subtract or scale it again.
- **#303** — NEVER initialise a payout-leg status to a TERMINAL value with the transfer behind a condition; use an exhaustive branch chain, and a non-terminal status is safe only if EVERY retry path accepts it.
- **#377** — `"Pending"` is a POST-TRIGGER value the sweep RETRIES; a backfill must write **NULL** for a leg that has not been triggered. **#380** — when a guard stops short-circuiting, re-audit every sibling leg's terminal check. **#441** — the same rule read from the other end: when a payout is DEFERRED to a later payment, the legs staying NULL is the whole mechanism, and the sweep's candidate scan may already be picking the row up on some *other* satisfied precondition (the tax final retainer: `retainer_receipt_number` is stamped at the INITIAL payment) — so only the retry-only gate keeps it from paying early. Never pre-stamp a deferred leg, and name which gate is actually holding it.
- **#265** — a stranded-leg rescue must verify the UPSTREAM leg resolved first. **#277** — a backfill of an already-collected payment MUST settle every leg its sweep can rescue. **#362** — a pre-settled leg is skipped FOREVER; check Stripe Transfers before assuming either way.
- **#335** — Payment Continuation is a SECOND write path into `pipeline_map1`/`client_tax_plans` and must carry the strategic split; a missing one is INVISIBLE (NULL reads as "no partner", nothing reports it).
- **#327** — Stripe REDELIVERS a webhook whose 200 we were too slow to return and there is NO event-id dedupe; name the column that proves a side effect already happened and check it first. **#470 is the same rule for a TIMESTAMP, which nobody defends:** a provider redelivers its terminal event, so an unconditional `col = now()` in that branch silently re-dates history on every redelivery — write `existing || now` (BoldSign re-stamped the CEO countersign date, invisibly, on the column the balance display gates on). **#473** — **when one row gains a SECOND collection on the SAME customer, every webhook branch keyed on the customer must split on a `payment_kind` carried on the SESSION metadata** (in `checkout.session.completed` the PaymentIntent has not been fetched yet, so the session is all you have — set the kind on BOTH), the new branch goes AHEAD of the old one and the old one keeps its own positive guard, and **every generic failure resolver must SKIP the new kinds** or it writes a real status into the neighbouring leg's column. Nothing here fails loudly. **#228** — off-session idempotency keys must be LOGICAL/date-less. **#15** — rotate keys per RETRY, never per logical charge.
- **#469** — **a column DEFAULT is a value a reader cannot distinguish from a written one** (not NULL, not zero, right type, plausible range), so a figure derived from it renders confidently wrong before anyone fills it in: `payment_amount DEFAULT 4000` printed *"nothing further due"* on unpriced onboardings. **Gate every derived figure on the column that proves the write happened** (here `agreement_signed_by_ceo_at`) and say so on screen; when you add such a default, name its "written for real" event in the same breath. **#478** — **a field that STORES a charge date must not be EDITED as one:** the member has already paid for the period they are in, so take *"when does it start"* as input, derive the renewal with the **same helper the sweep uses**, preview the derived date on screen, and refuse a start whose renewal is already past — a "next charge date" box invites a second deduction (a yearly GC sub was eight days from taking 10 more credits). **#429** — a NULL in an optional column can BE the switch that selects the OLD money behaviour (`charge_day` on a monthly transfer: set = save-only link + year scheduled on that day; NULL = the legacy pay-at-the-link charge). Nothing on screen says which mode a row is in, so a missed backfill or an omitted form key silently bills the wrong way — **prove such a backfill with a query, never a spot-check**, and when a column gains a SECOND writer, state which one owns it in which plan state.
- **#433 / #240** — **`members.suspended` / `paused` / `membership_suspended` GATE payouts, not just displays** (v778): every member payout engine must carry all three in its member `select` and hold the MEMBER leg only. Adding a NON-TERMINAL status (2026-08-24 also `lic_payment_status='scheduled'` — a subscription with zero money moved, **#437**, where PostgREST `.neq` silently drops the NULL rows you need) means teaching **every** enumerating predicate by hand — engine `isResolved`, every sweep pickup list, every FE `PAYABLE`/`PENDING` set — or the leg strands silently; export the list from the engine and import it into the sweep. **#432** — SpecRev's sandbox mode is the GLOBAL `"MAP 1"` toggle, so #251's client-keyed test-member force does NOT cover it, and firing it on a member with a half-built account REAL-SENDS `SPECREV_connect_setup`.
- **#463** — **one constant plus a strict comparison defines exactly TWO bands.** Adding a third needs **two NAMED edges** (a floor and a ceiling, both strict, so every boundary total is answerable from the constants and not from someone's `>` vs `>=`) and **ONE shared, non-throwing core that every consumer imports** — pricing, the amend handler, the deck, the invoice labels, the FE mirror; enumerate them first, because the consumer that cannot tolerate a throw is what proves the range check belongs in the wrapper, not the core (#453). **A DISPLAY LABEL must be derived from the ARITHMETIC, not from the shape flag:** *"Retainer (50%)"* printed on every non-3-payment plan because "not 3-payment" had always meant "even split", and a lopsided 2-payment plan would have contradicted itself in writing to the client — test `retainer × 2 === total` in whole cents (1c tolerance). And **reuse an existing storage shape if one exists** rather than adding a column or a boolean, or the new band becomes a new branch in every consumer.
- **#287** — purchase-email policy: card = receipt only, ACH = confirmation + docs at settle, check = both at clear. Gate PLACEMENT is load-bearing. **#475 is the ACH policy's hard edge: WIDENING a payment method widens what "completed" MEANS.** Unpinning `verification_method` (#298) lets a client type account + routing numbers, and Stripe then fires `checkout.session.completed` at **SUBMIT** with the PaymentIntent in `requires_action` and **no debit attempted** — so **read the PI's own `status`; the session's arrival is not evidence of a payment**, and the confirmation body that says *"we have received your payment"* becomes a lie you send (#468). Record the sub-state in a **nullable SIDE-COLUMN, never a new status value** — a side-column is invisible to code that does not read it, so every settle branch, failure branch, sweep, resolver and FE status map needs zero changes, where a fourth status value means auditing all of them (#371). And **whenever you expose a path that can EXPIRE, find the event the expiry actually emits** — micro-deposit expiry is `payment_intent.canceled`, not `payment_failed`, so a row would otherwise sit at `processing` forever with no bell. Two traps ride along: a metadata field two producers now set no longer means what its original consumer assumed (`payment_number='1'` made the generic first-payment resolver skip a cancelled P1), and a template discriminator must join the handler's explicit `.select(...)` in the SAME edit or the predicate is silently, permanently false (#448). **#482 is the narrowing that widening needed, and it is the general rule: a CANCELED PaymentIntent is not a failed payment unless the row was BOOKED against it** — Stripe mints the PI when a Checkout page merely OPENS and cancels it (`automatic`, indistinguishable from an expired verification) 24h after that page expires unpaid, so `!== 'succeeded'` reads *absence* of a payment as evidence of a *failed* one; gate on `=== 'processing'`, the row's own booking (#431/#444's positive allowlist, on the write side), and remember that a terminal status on a column a durable client link reads is a write to the client's ACCESS, not just to a report (it killed Pat Hurst's `/tax-pay` link, 2026-09-09).
- **#282** — `allocateDocNumber` returns its candidate even when the reservation INSERT fails; verify the reservation landed or you issue duplicate accounting numbers. **#315** — a multi-period collection must change a row's AMOUNT, never the row COUNT.
- **#454** — **copying an id to route the money silently re-points every OTHER surface that reads it.** A corporate member borrows their lead's `stripe_account_id` by a straight copy (`stripe_account_linked_from` is a MARKER — the four payout engines were unchanged, the copy IS the routing), and that same copy turned an admin setup email AND the durable public `/payout-setup` token into onboarding links **into the lead's Stripe account**, and the by-`destination` payout listing into a leak of the lead's and every sibling's history. **Before making one row borrow another's identifier, enumerate every reader of the borrowed column and split them into "meant the value" and "meant WHOSE it is"** — the second group is all wrong, and none of it fails a build, a type-check or a click-through of the feature you just built.
- **#159 / #317 / #268 / #479** — verify `capabilities.transfers === 'active'` before a Connect transfer — **an account id is NOT a payable account** (the admin's "Set Up Payment Details" button creates the Express account on the click, so `stripe_account_id` is set long before the member can receive anything), so probe it from ONE shared helper that never throws, park a half-built account **non-terminally** where the sweep already retries it, and gate the held BELL on `members.connect_setup_email_sent_at` — once the ask is out there is nothing to ask, so stay silent and CLEAR the stale FAILED bell. Before copying "park it, the sweep retries" into a neighbouring engine, read that engine's sweep and name the status it picks up (PIP's `Pending` is not swept, which is why PIP was left alone). every account link must append `collection_options[fields]=eventually_due` (else a silent $3,000 cap); never email a raw `connect.stripe.com` link — use the durable `/payout-setup?token=` page.
- **#396 / #397** — reminder ladders count BUSINESS days via `businessDelayCutoffIso`; it walks whole weekdays FIRST then subtracts fractional hours, and **a bigger `days` must always yield an earlier-or-equal cutoff**. The calendar survivors are deliberate — see [architecture/07-server-chains.md](architecture/07-server-chains.md).

**Data loss**
- **#206** — Supabase blocks direct SQL `DELETE FROM storage.objects`; delete vault files through the Storage API. **#305** — `client_tax_progress.tax_specialist_id` is FK ON DELETE SET NULL and NULL means PLAN-LEVEL, so a naive specialist delete orphans progress rows and corrupts plan state.
- **#187** — ALWAYS destructure `{ data, error }` in webhook/automation code; otherwise a real DB failure is indistinguishable from "no rows" and fails 100% silently. **#427** is the same family one level up: after calling anything that UPDATES a row you are holding, your copy is STALE — re-read before passing it to any consumer keyed on the mutated column (a stale key filters to zero rows just as silently, and "fix the filter" breaks the money math instead). **#215** — multi-row inserts fill missing keys with NULL, not the column default.
- **#431 / #444** — a status vocabulary in a migration comment is a SNAPSHOT, not a constraint (these columns are bare `text` with no CHECK). Before gating a DESTRUCTIVE action on a status, enumerate the values from every writer of that column, use a positive allowlist not a denylist, and back it with a column that is directly true of the thing you care about (a non-null PaymentIntent id beats any status string). **The money-side corollary: a status DENYLIST in a CHARGE sweep charges every value it has never heard of** — the 2026-08-26 cancel button would have had the nightly MAP 1 sweep charging cancelled installments, because `skipStatuses` predated `'cancelled'`. **Invert to a positive charge-only-on-EMPTY test BEFORE introducing any new terminal status**, and read an unknown status as "someone else owns this slot", never as "charge it".

**Cross-repo contracts**
- **#339 / #460** — the tax step machine (now `utils/tax-plan-steps.ts`, called by `overview-tax.ts` AND the planner portal) is the BACKEND MIRROR of the FE `isTaskStatused`; add both branches in the same change, and remember `computeTrack` is POSITIONAL — warnings, `next_action` and `next_actions` are all a function of ORDER. **#460 is the same failure INSIDE one component, which no cross-repo check catches:** the allocation step has THREE done-tests — the step's own dot (either slot), `isTaskStatused` (planner slot ONLY, and it drives the phase pills + hero counts), and the backend catch-all (progress row, so either slot) — and on a team-member-only plan they disagree. When you split a column, enumerate every done-test of that step; the one driving the visible dot is rarely the one driving the counts.
- **#414** — a plan MIGRATED from the legacy system never got its branch column backfilled, so a step machine that keys a whole branch on that one column points every migrated row weeks into the past. **Prove a branch by the columns that branch itself writes** (agreement sent / signed / paid / decided), not by the decision field alone — and check for legacy rows before trusting any single-column branch test.
- **#403** — a **terminal/negative** outcome can SATISFY a "cascade complete" predicate, so `locked: !cascadeDone` unlocks exactly the closed records. Test the decline/refund/stop state FIRST, and back the UI lock with a handler 400 — the lock alone is choreography (#353).
- **#404** — re-invoking a confirmation-email handler to RESEND re-arms every reminder ladder it stamps. A reschedule must pass an explicit `reschedule` flag and every ladder-arming side effect must sit behind `!reschedule`; the failure is silent (a chase restarts on a form the recipient already has).
- **#365 / #179** — an action-required bell (`dismissible:false`) is a CONTRACT: a clear site for every satisfying path, a satisfied-on-fire guard, and a title nobody edits. Only the completing handler can clear it. **#176** — every bell goes through `notifyByRule` + a `notification_rules` seed. **#313** — one event serving two audiences needs TWO rule keys. **#481** is the mirror: one audience getting TWO bells about one event — when an action-required bell is raised for the same recipient about the same thing, make the raising function RETURN whether it fired, order it BEFORE the FYI, and drop that recipient (never the whole bell — the other recipients still need it).
- **#438** — a JS `String.replace` **replacement STRING** treats `$1`, `$&`, `` $` `` as capture references, so any money-bearing substitution silently corrupts itself (`$12,500.00` → the first capture group + `2,500.00`). **Every token substitution carrying a user- or DB-supplied value must use a replacer FUNCTION** (`() => value`), not a string. Bit twice in one branch.
- **#324 / #413** — a recipient ROLE TOKEN does NOTHING unless the HANDLER passes it (in template ctx, or in `notifyByRule`'s `dynamic` map), and it is dropped SILENTLY. **To know who receives a templated email or a bell, read the HANDLER — the template row and `notification_rules.default_recipients` are documentation, not routing.** A rule's `recipients` override wins only when non-empty AND resolvable, else the code default; the fallback direction is safe, keep it.
- **#411** — a bell's TITLE is the clear contract, so its RECIPIENT is FREE: re-address a live action-required bell by moving `defaultRecipients` and **leave the title (and the rule KEY) alone even when it now names the wrong role**. The clear site matches title-prefix + client_id and never reads recipient, so it retires both vintages with no cutover window.
- **#356** — a template's Draft/Send mode is keyed by `(pipeline, template_name)` in TWO places per consumer; a mismatch looks exactly like a deliberately-Draft row and the mail sits in Drafts forever with no error. **#325** — exactly THIRTY-ONE rows are `send_mode=true` (11 → 17 on 2026-09-04 → 31 on 2026-09-08); editing one reaches a real person with nobody in between. **#428** — a `send_mode` flip is a **UI edit too**: grep the FE for every draft-era success string on that template's callers ("send the draft from Gmail" invites a duplicate real send), and give any real-sending admin button an idempotency stamp + a `force` override, with the guard BEFORE every side effect.
- **#382 / #392 / #323 / #459** — a user-visible LABEL can be a lookup key, a DISPLAYED name can diverge from the STORED name, and a task NAME can be exact-matched across both repos with no compile-time protection. Grep both repos before renaming anything. **#459, the render-side twin:** a mode-keyed CATCH-ALL row (`if (readOnly) return …`) placed mid-renderer silently preempts every branch below it and turns their own mode arms into dead code that reads as live — and it stayed invisible for a year because only ONE preempted step stores a **person's name** in its status column, where `statusColors[name]` misses and falls back to the "not done" grey. **Never feed a free-text column to a status→colour/label map**, and put a mode catch-all AFTER every branch that renders that mode itself.
- **#342** — an external asset the code reads BY NAME is coupled to the deploy: content-only assets hot-swap, structure-bearing ones need a NEW versioned name + a lockstep deploy, uploaded FIRST. **Diff against the object the LIVE FUNCTION READS, never against your build artifact** — 2026-08-18's template v4 was byte-identical to a backup already in the bucket and still needed a new version, because relative to the hot-swapped live object it restored a token SITE (#336). **#480** — **a wording change on a FIXED-WIDTH text box is a geometry change** (seven extra characters wrapped and overlapped the row below on three slides): widen by measurement AND set `wrap="none"`, replacing `<a:spAutoFit/>` with `<a:noAutofit/>` so an editor cannot re-fit the `cy` the handler's thresholds are measured against — and **when a part's shape SET changes, re-derive every per-part count the code asserts** (12/14 → 9/10) and keep a NEGATIVE CONTROL that fails the new constants against the old master. **#453** — an artifact that MIRRORS a money process must **import** that process's constants, never re-type them (a second copy of a number that must agree eventually disagrees, and the copy nobody executes is the stale one); and when two generation-time surgeries land on one part, the ORDER is a contract and each needs an assertion derivable **without** reference to the other, or a silently no-opping step is quietly agreed with by the check that should have caught it.
- **#406** — a "completed on" cell fed by a scheduling field (`_send_date`, `_meeting_date`) displays a FUTURE date and reads as fact, not bug; a step whose work is *scheduling* dates from when it was scheduled and must not move later. Fix the FE and its `overview-tax.ts` mirror in the SAME change — they disagree silently, both dates being plausible.
- **#407** — two asks answered at DIFFERENT times need DIFFERENT bell titles (one prefix = one clear contract); two keys may share a title only when the instruction is identical. To add a second ordering to a one-way flag, put a DISCRIMINATOR beside it (NULL = original) so everything keyed on the flag stays route-blind.
- **#452** — **SPLITTING an overloaded column into two silently invalidates every OTHER guard that read it as "somebody/anything is set", and the guards that break are the ones you did not touch.** Before splitting, grep every read and sort them into "meant the specific thing" (safe on the narrowed column) and "meant anybody" (must now test BOTH) — an error MESSAGE naming both meanings (*"Allocate a Team Member / Tax Planner"*) is the loudest tell that a guard is in the second group. A migration that MOVES rows out of the old column turns each such guard into an immediate live regression on exactly the rows it moved. Shipped that way in v793 and **found by the wrap-up DOC AUDIT, not by any gate** — the build, `deno check` and the live click-through all passed, because they exercised the new paths and never re-walked the old ones; fixed in v794.
