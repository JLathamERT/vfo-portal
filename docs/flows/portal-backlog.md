# Portal Backlog (More ▾ → Portal Backlog)

> Built 2026-11-17 from Jake's Workbench card *VFOS Portal Backlog Tracker*, with Paxton's decisions. It replaces the "VFO Portal Update Requests" Google Sheet. Tables: [tables/portal-backlog.md](../tables/portal-backlog.md). Actions: [architecture/05-api-action-catalog.md](../architecture/05-api-action-catalog.md) *Portal Backlog*. *(v: 2026-11-24)*

> **The third lane column is labelled Review** (Paxton 2026-11-24; it read "Done" until then). It is still stored as `progress = 'done'` (with `done_at`), and "Done by …" on Ready to announce and Live cards still names who did the work. Where this doc says Review it means that column; the drawer's approve / deny **Review** card is a different thing.

## What it is

Any admin files a request for a change to the portal. A superadmin (`constants/superadmin.ts`, today Jake and Paxton) approves or denies it. An approved request moves across a board until the work is done and Live (announced first when it matters), then it is archived.

- **Who sees it:** every admin. The More ▾ entry is never gated by `allowed_tabs` and has no `TAB_ACTIONS` key, so it is not on the Admin Editor's list. Members, clients, specialists and tax planners never reach it (every action is in `ADMIN_ONLY_ACTIONS`, is in no other portal's allowlist, and each handler also refuses a non-admin `callerRole`).
- **What any admin can do:** see every request, file one (+ New request), like requests (see *Likes*), and edit or withdraw their OWN request while it is pending. The rest of the board is read-only for them: the write-up (on an approved request) shows as text ("No write-up yet." when there is none) and there is no Archive button (2026-11-23, Backlog 2b).
- **What only a superadmin can do** (`SUPERADMIN_ONLY_ACTIONS`, re-checked in the handler): approve, deny and reopen; edit any request; move and reorder cards; Sort by priority and Sort by likes; set the likes per person; write the "What it does" write-up; Mark as announced; archive a Live item; restore from the archive; set the release importance; add a task and change any task (see *Tasks*).

## Tasks (2026-11-23, Workbench Backlog 4a / 4b / 4c)

A **task** is a second kind of item (`portal_requests.kind = 'task'`; every request is `'request'`): Jake's and Paxton's own work, put straight onto a lane without a request or a review. Every admin sees tasks; only a superadmin adds or changes one.

- **Born approved** (`reviewed_by_admin_id` = the creator, `requested_on` today ET), with no urgency, importance or requested assignee. It is never pending, so it never shows on the Requests tab and cannot be approved, denied, reopened (409 "Tasks aren't reviewed.") or withdrawn (409 "Tasks can't be withdrawn.").
- **Fields:** title (1–140), description (1–4000), departments optional (none is fine), an optional **due date** (`due_on`, past dates allowed).
- **Always in a lane:** never Approved but unassigned. The Move card has no "No one (Unassigned)" for a task, a task dragged onto that column is refused on the page ("A task always belongs to someone. Assign it to a lane instead."), the server refuses it (400 "A task always belongs to someone.") and so does the table (`portal_requests_task_assigned`).
- **Same path as a request:** To do → Working on → Review → Ready to announce → Live → Archive (or Review → Live), and Restore (see *Live and What's new*). **The write-up is optional for a task** (Paxton 2026-11-23, changed from spec 4a): it may enter Ready to announce without one, and one there may have it cleared.
- **Adding** (`TaskModal.jsx`, superadmins only): **+ Add task** on the right of the Tasks board toolbar (not on Requests or in the Archive), or the **+** on any lane's To do header. The form has Title (with the request form's n / 140 counter), Description, Departments (optional), Due date (optional) and **Assign to**: "Me (<name>)" first and the default, then the other superadmin, never no one; a lane's + picks that lane's person. The task lands as the **first card** of that person's To do (`topKey`). Editing a task opens the same form without Assign to (moving is the Move card or a drag) and keeps the card where it is.
- **How it looks:** a solid navy **Task** tag before the title (card, Requests table row, archive row, details header); no score pills (dashes in the Requests table); a due chip "Due 5 Dec" that turns red "Overdue · 5 Dec" once the date has passed and the task is not yet in Ready to announce or archived; "From <creator>" on the card and a **From** field in the details when the creator is not the assignee ("a former admin" if they left). The details' Review card becomes **Added**: "Task added by <creator>, <date>". History starts "Added the task" (`task_created`).
- **Sort by priority** puts the column's tasks on top in their current order, then the requests by priority; a request placed by priority never goes above a task.
- **Counts:** the hero counts **requests only** (Paxton 2026-11-23); What's new does include tasks, with their tag.
- **Bells:** a task's only bell is `BACKLOG_assigned` (see *Bells*). It never sends `BACKLOG_new_request` or `BACKLOG_ready_to_announce`.
- **An admin who leaves:** `assignee_admin_id` is `on delete set null`, which `portal_requests_task_assigned` refuses for a task, so before deleting a superadmin's `allowed_admins` row, move or archive their tasks.

## Live and What's new (2026-11-23, Workbench Backlog 5a / 5b)

Jake's point 5: a place listing, in order, what has gone live, with big news standing out so the team knows what to tell members. Requests and tasks alike.

- **The Live stage** (`progress = 'live'`, after Ready to announce). Two ways in, and nowhere else (400 "Only a Done or Ready to announce item can go Live"):
  - **Ready to announce → Live = Mark as announced** (big changes): `AnnounceDialog.jsx` asks for the **Announced on** date (today by default, never in the future), an optional note and the **Release importance**. They are saved with the move (`announced_on` / `announce_note`; 400 without a valid date). A drag from Ready to announce into Live, or the Move card's Live option, opens the same dialog first; Cancel leaves the card where it was. History: "Marked as announced on <date>: now Live" (`announced`).
  - **Done → Live** (small changes, never announced): no write-up needed, no dialog. History: "Moved from … to Live" (`went_live`).
  - `live_at` = the first time it went Live, never cleared (like `done_at` / `ready_at`). A Live card keeps its assignee ("Done by …") and shows "Live <date>". Moving it back out clears nothing but the column.
- **Archive happens from Live only**, with a plain **Archive** button (superadmins, no dialog): 409 "Only a live item can be archived." from anywhere else. Ready to announce cards offer **Mark as announced** instead. **Restore** puts an item back in **Live** and keeps its announced date and note. An item archived from Ready to announce before 2026-11-23 restores to Live with the date it was archived with.
- **The board:** Live is a second shared pool after Ready to announce. From 1280 px the grid is Approved but unassigned · lanes · Ready to announce · Live at **2 : 3 : 1 : 1**. Approved but unassigned is two columns wide with its cards two across, so the two ends match (Paxton 2026-11-23). There, a drop lands before the card under the pointer's row and side, and the whole column outline lights up instead of the between-cards line. Below 1280 px everything stacks, Live under Ready to announce.
- **What's new tab** (`AnnounceTab.jsx`; named by Paxton 2026-11-23, Jake's spec called it Ready to announce): the third pill after Tasks and Requests, with its count (Ready + Live, tasks included). It has no hero (like Tasks, after #646) and a toolbar of Filter + Archive. Two sections, **Ready to announce** and **Live**, each with a count chip and an empty line ("Nothing waiting to be announced." / "Nothing live yet.").
  - Each item is a full-width announcement card: the Task tag, the release-importance pill, the title, department chips, the whole write-up (or "No write-up — minor change."), and a meta line ("Done by … · Ready since …" / "Live … · Done by …", plus "Announced …" and the note).
  - Superadmins get Mark as announced / Archive on the right. Clicking the card opens the drawer.
  - **It replaced the Requests tab's Ready to announce list** (Paxton 2026-11-23): Requests now shows only the requests waiting for review, with no New requests / Ready to announce pills. A bell link to an item in Ready to announce or Live opens its drawer on What's new.
- **Release importance** (`release_importance`: `big` / `normal` / `minor`, default `normal`; always labelled "Release importance", because the 1-5 Importance score is a different thing):
  - **Setting it:** a superadmin sets it at any stage, archived included (never on a withdrawn request), with the select at the top of the drawer's **Announcement** card (the drawer only: a Requests tab row dropdown has no Announcement card, Paxton 2026-11-24). It saves at once ("Saved") and history reads "Set release importance to Big news". The Mark as announced dialog has the same select. Regular admins see the level as text.
  - **Automatic Minor:** Done → Live turns a still-Normal item into **Minor** (history note "went straight to Live"). It can be changed back.
  - **How it shows:**
    - Every card on the Tasks board and on What's new shows a pill: gold **Big news**, blue **Normal** or grey **Minor** (`ReleaseImportancePill`, Paxton 2026-11-23).
    - The Requests rows, Archive rows and the row-dropdown header show the gold Big news badge only (`BigNewsBadge.jsx`; the text colour is the `--vfo-gold-text` token, light and dark).
    - On What's new each section lists Big news first, then Normal, then Minor, newest first within each (`byReleaseThenNewest`). Big news cards get a 2 px gold border, a gold tint and an 18 px title. Minor cards are muted: no shadow, a 13 px write-up, chips at 75%.
- **Archive rows** read "Announced on <date>" with a green **Announced** pill when announced, else "Live <date>" with a teal **Live** pill. The Show filter reads Archived and denied / Archived / Denied.

## Likes (2026-11-23, Workbench Backlog 7a / 7b / 7c)

Jake's point 7: let the team show what they want built, with a small number of likes each, so the totals show what many people want rather than what one person thinks is important.

- **What can be liked: requests only, never a task** (Paxton 2026-11-23, deciding Jake's open question in spec 7a). Any request that is not archived, withdrawn or denied: pending, or approved in any column, Live included. Every admin can like, superadmins included, their own requests included; one like per person per request (`portal_request_likes`).
- **The button** (`backlog/LikeButton.jsx`): a thumbs-up pill with the count (no number at 0), outline and muted when you haven't liked it, filled blue when you have; tooltip Like / Unlike. It is in the Requests table's **Likes** column (and on a phone row card), at the top right of every request card on the Tasks board, and in the details' Description card beside **"Liked by You, Ana Ruiz and Sam Lee"** (you first, then A to Z; "No likes yet" when none). A click never drops the row open, opens the drawer or starts a drag. It flips at once and the server confirms; a refusal flips it back with the server's message in the red notice. No reload, no history row, no bell.
- **The cap (7b):** each admin holds at most **N active likes**. A like is **active** while its request is pending, or approved in To do (Unassigned included) or Working on, and not archived. It frees up when the request reaches Review, Ready to announce or Live, or is denied, withdrawn or archived; the like itself stays and still shows. Moving a request back counts its likes again, which can put someone over N: nothing is removed, they just can't add a like until they're under. A like on a Review / Ready / Live request never counts. A like over the cap gets 409 "You've used all N of your likes. Unlike something, or wait for a request you liked to be done."
  - **N starts at 5** (Paxton 2026-11-23; spec 7b proposed 3) and is 1–20. A superadmin sets it with the **"Likes: N each"** link on the Requests and Tasks toolbars (`backlog/LikeCapDialog.jsx`). Lowering it removes no likes.
  - Every admin sees **"k of N likes left"** next to Sort on Requests and next to Archive on Tasks, amber at 0. At 0, every unliked button on a request where the like would count is greyed with the cap tooltip; your own liked buttons and buttons on Done / Ready / Live requests stay usable.
- **Sorting by likes (7c):** the Requests tab's Sort dropdown has **Likes: Most** (ties to the older request), and its **Likes** header sorts most-liked first on the first click. On the Tasks board a superadmin gets **Sort by likes** beside Sort by priority (a column with 2+ cards): a one-time re-number of that column, most likes first, ties by the priority key, with tasks staying on top in their own order as in Sort by priority. Later likes don't move cards until someone clicks it again. Likes never enter the priority score or the default board order.
- **The Archive** shows a request's count as a plain pill, with no button.

## The rules (all enforced by the backend)

| Rule | Where |
|---|---|
| Title 1–140 characters, description 1–4000, at least one department from the list, urgency and importance whole numbers 1–5 | `validateFields` (`actions/portal-backlog/shared.ts`) + table checks |
| The requester and the date come from the session (`requested_on` is today in America/New_York) | `portal_request_create` |
| "Assign to" is only Jake, Paxton or no one; it is used once, at approval | `validateFields`, `portal_request_review` |
| Approve lands in the picked person's To do if they are still a superadmin, else in Approved but unassigned, placed by priority | `portal_request_review` |
| Deny needs a reason; a denied request leaves the board and the counts and shows in the archive | `portal_request_review`, `portal_backlog_load` / `portal_backlog_archive_load` |
| Only To do can be unassigned; a card in Ready to announce or Live keeps its assignee | `portal_request_move` |
| Live is entered only from Done (no write-up needed; a Normal release importance becomes Minor) or from Ready to announce with a valid announced date that is not in the future (+ optional note and release importance) | `portal_request_move`, `parseAnnouncedOn` (`shared.ts`) |
| Release importance is big / normal / minor, set by a superadmin at any stage except withdrawn | `portal_request_importance_set`, table check `portal_requests_release_importance_check` |
| A card enters Ready to announce only with a write-up, and one there cannot have it cleared (a task: optional) | `portal_request_move`, `portal_request_writeup_save` |
| A task: added by a superadmin only, born approved in a lane's To do (top), no urgency / importance, departments optional, an optional due date; never reviewed, withdrawn or unassigned; changed by a superadmin only | `portal_task_create`, `validateTaskFields` (`shared.ts`), `portal_request_review` / `_withdraw` / `_update` / `_move`, table checks `portal_requests_task_shape` / `_task_assigned` |
| Priority = urgency + importance, highest first; ties to the older request date, then the older id. Tasks sit above every request, in their own order. Ready to announce and Live are each one shared pool | `priorityKey` (`shared.ts`), SQL `portal_backlog_resort` |
| Only a Live item is archived (409 otherwise); a restore puts it back in Live | `portal_request_archive`, `portal_request_restore` |
| A like: requests only, not archived / withdrawn / denied (409 otherwise); at most N active likes per admin, counted and written under a per-admin lock so two quick clicks can't pass it; unlike always works; N is 1–20, set by a superadmin | SQL `portal_request_like_set` via `portal_request_like`; `portal_backlog_settings_save`, table check on `portal_backlog_settings.like_cap` |
| Sort by likes: like count, then the priority key; tasks on top | SQL `portal_backlog_resort(…, p_order => 'likes')` via `portal_backlog_resort` `order_by: 'likes'` |
| A withdrawn request disappears from every view and count (the requester's own come back in `my_withdrawn`, unused by the page) | `portal_backlog_load` |

**One write path.** Every write goes through the SQL function `portal_request_apply(p_id, p_set, p_expect, p_events)`: the change and its history rows in one transaction, and `p_expect` is the state the handler decided on. If someone changed the request in between, it raises `portal_request_conflict` and the handler answers **409** ("This request changed while you were working on it. Reload and try again."), so two superadmins cannot both approve or both move a card.

## Bells (team notifications are bells only — TEAM_RULES §8)

Five `notifyByRule` rules, area **Portal Backlog**, kind `bell`, FYI, `dismissible`, pipeline `PORTAL_BACKLOG`, no `email_templates` rows. Each is sent with `forceRecipients`, so the Notification Editor can switch it off but not re-route it. The link is `/admin?tab=portal_backlog&request=<id>`: `AdminPortal.jsx` passes it to the panel. A pending request opens the Requests tab with its row dropped open and scrolled into view (clearing a lens, filter or search that would hide it); one in Ready to announce or Live opens its drawer on What's new; any other request on the board opens its drawer on the Tasks tab, and an archived one its drawer in the archive.

| Rule | To | Title | Message |
|---|---|---|---|
| `BACKLOG_new_request` | every superadmin except the requester | "<requester> submitted a portal request" | the title |
| `BACKLOG_approved` | the requester | "Your portal request was approved" | the title |
| `BACKLOG_denied` | the requester | "Your portal request was denied" | the reason |
| `BACKLOG_assigned` | the new assignee, when a card enters their lane (approval with them picked, or a move from Unassigned or the other lane), or a task is added straight into the other superadmin's lane | "<actor> assigned you a portal request", or "<actor> assigned you a task" for a task | the title |
| `BACKLOG_ready_to_announce` | the requester, when a REQUEST enters Ready to announce (never a task) | "Your portal request is ready to announce" | the title (+ "done by …") |

Never to the person who acted, and never to someone no longer in `allowed_admins` (re-read at send time: `bellAdmin` in `shared.ts`). Going Live (Paxton 2026-11-23: no bell, as spec 5a proposed), archive, restore, reorder, edits, write-ups, release importance, likes and the likes-per-person setting send no bell. A failed bell is logged and never undoes the change. On the test site every bell goes to the tester with the `TEST - meant for:` line.

## The sheet import

`scripts/portal-backlog-sheet-import.sql` (edge repo — it holds staff names and request text, so it stays out of this public repo). Generated once from the sheet's CSV export: 89 rows, the 25 Approved / Completed rows skipped, 50 pending, 1 denied ("Denied in sheet"), and the 12 On Hold + 1 In Progress rows in Approved but unassigned in priority order (history note "Imported – was On Hold" / "– was In Progress"). The import first titled each row with the first eight words of the request + "...". On 2026-11-22 (Workbench *Backlog 6a*) `scripts/portal-backlog-title-fix.sql` (edge repo) replaced the 55 cut-off titles with short titles Paxton approved (run on the test site and on live 2026-11-22), keyed on `sheet_row` and only where the old title was still there; it writes one History row each, sends no bell and leaves descriptions alone. The import script now carries the approved titles, so a re-run cannot bring "..." back. Requesters are matched to `allowed_admins` by name. It writes the tables directly (no bells), keyed on `sheet_row`, so a second run adds nothing. Run on the test site 2026-11-17; run on live at release, after both migrations.
