# Portal Backlog (More ▾ → Portal Backlog)

> Built 2026-11-17 from Jake's Workbench card *VFOS Portal Backlog Tracker*, with Paxton's decisions. It replaces the "VFO Portal Update Requests" Google Sheet. Tables: [tables/portal-backlog.md](../tables/portal-backlog.md). Actions: [architecture/05-api-action-catalog.md](../architecture/05-api-action-catalog.md) *Portal Backlog*. *(v: 2026-11-23)*

## What it is

Any admin files a request for a change to the portal. A superadmin (`constants/superadmin.ts`, today Jake and Paxton) approves or denies it. An approved request moves across a board until the work is done and announced, then it is archived.

- **Who sees it:** every admin. The More ▾ entry is never gated by `allowed_tabs` and has no `TAB_ACTIONS` key, so it is not on the Admin Editor's list. Members, clients, specialists and tax planners never reach it (every action is in `ADMIN_ONLY_ACTIONS`, is in no other portal's allowlist, and each handler also refuses a non-admin `callerRole`).
- **What any admin can do:** see every request, file one (+ New request), and edit or withdraw their OWN request while it is pending. The rest of the board is read-only for them: the write-up (on an approved request) shows as text ("No write-up yet." when there is none) and there is no Archive button (2026-11-23, Backlog 2b).
- **What only a superadmin can do** (`SUPERADMIN_ONLY_ACTIONS`, re-checked in the handler): approve, deny and reopen; edit any request; move and reorder cards; Sort by priority; write the "What it does" write-up; archive a request in Ready to announce; restore from the archive; add a task and change any task (see *Tasks*).

## Tasks (2026-11-23, Workbench Backlog 4a / 4b / 4c)

A **task** is a second kind of item (`portal_requests.kind = 'task'`; every request is `'request'`): Jake's and Paxton's own work, put straight onto a lane without a request or a review. Every admin sees tasks; only a superadmin adds or changes one.

- **Born approved** (`reviewed_by_admin_id` = the creator, `requested_on` today ET), with no urgency, importance or requested assignee. It is never pending, so it never shows under New requests and cannot be approved, denied, reopened (409 "Tasks aren't reviewed.") or withdrawn (409 "Tasks can't be withdrawn.").
- **Fields:** title (1–140), description (1–4000), departments optional (none is fine), an optional **due date** (`due_on`, past dates allowed).
- **Always in a lane:** never Approved but unassigned. The Move card has no "No one (Unassigned)" for a task, a task dragged onto that column is refused on the page ("A task always belongs to someone. Assign it to a lane instead."), the server refuses it (400 "A task always belongs to someone.") and so does the table (`portal_requests_task_assigned`).
- **Same path as a request:** To do → Working on → Done → Ready to announce → Archive, and Restore. **The write-up is optional for a task** (Paxton 2026-11-23, changed from spec 4a): it may enter Ready to announce without one, and one there may have it cleared.
- **Adding** (`TaskModal.jsx`, superadmins only): **+ Add task** on the right of the Tasks board toolbar (not on Requests or in the Archive), or the **+** on any lane's To do header. The form has Title (with the request form's n / 140 counter), Description, Departments (optional), Due date (optional) and **Assign to**: "Me (<name>)" first and the default, then the other superadmin, never no one; a lane's + picks that lane's person. The task lands as the **first card** of that person's To do (`topKey`). Editing a task opens the same form without Assign to (moving is the Move card or a drag) and keeps the card where it is.
- **How it looks:** a solid navy **Task** tag before the title (card, Requests table row, archive row, details header); no score pills (dashes in the Requests table); a due chip "Due 5 Dec" that turns red "Overdue · 5 Dec" once the date has passed and the task is not yet in Ready to announce or archived; "From <creator>" on the card and a **From** field in the details when the creator is not the assignee ("a former admin" if they left). The details' Review card becomes **Added**: "Task added by <creator>, <date>". History starts "Added the task" (`task_created`).
- **Sort by priority** puts the column's tasks on top in their current order, then the requests by priority; a request placed by priority never goes above a task.
- **Counts:** the hero counts **requests only** (Paxton 2026-11-23); the Requests tab's Ready to announce list does include tasks, with their tag.
- **Bells:** a task's only bell is `BACKLOG_assigned` (see *Bells*). It never sends `BACKLOG_new_request` or `BACKLOG_ready_to_announce`.
- **An admin who leaves:** `assignee_admin_id` is `on delete set null`, which `portal_requests_task_assigned` refuses for a task, so before deleting a superadmin's `allowed_admins` row, move or archive their tasks.

## The page (`src/components/admin/PortalBacklogPanel.jsx` + `backlog/`)

Styled like the Advisor KPIs page: the **Tasks / Requests** pills on top, then, on the Requests tab only, the navy `KpiHero` (lenses Pending review, Unassigned, To do, Working on, Done, Ready to announce, Total; requests only, never tasks), then a toolbar: on Tasks **Filter**, **Archive** and, for a superadmin, **+ Add task**; on Requests the **New requests / Ready to announce** pills (each with its count), **Archive** and **+ New request**. The Tasks board and the Archive have no hero and no + New request for anyone, superadmins included: the board is a progress view (2026-11-23, Backlog 2a; the hero left the board and the archive the same day). A lens filters the Requests tables only; the board shows every approved card whatever lens is picked, and the pick is kept when you switch tabs. Total counts pending requests and those on the board — denied and announced requests are in the archive.

- **Filter** (2026-11-23, Backlog 3b): Client Overview's `ListFilterButton`, on the Tasks toolbar and beside the Requests search box, with four groups: **Type** (Requests / Tasks, 2026-11-23), **Department** (the eleven names; a request matches when ANY of its departments is ticked, and a task with no department matches no tick), **Requester** (only people with a pending or approved request, A to Z) and **Assigned to** (the superadmins, any former admin still on a request, then Unassigned; the requester's pick while pending, the assignee once approved). Ticks within a group are OR, groups are AND. One filter is shared by Tasks and Requests (`backlogFilterGroups` in `backlogModel.js`). It narrows every board column (the lanes always show, drag still works, hidden cards keep their places) and the Requests tables; the hero counts follow the Department ticks only. It replaced the toolbar's single department dropdown and is not kept across page visits.
- **Tasks** (`BacklogBoard.jsx`): Approved but unassigned on the left, one lane per superadmin (To do / Working on / Done) stacked in the middle, the shared Ready to announce pool on the right. The lanes come from the server's `assignees`, never from React. Below 1280 px the two tall columns sit above and below the lanes; below 768 px one lane shows at a time with a lane picker. The page grows to 1800 px.
- **Requests** (`BacklogRequestsTab.jsx`, 2026-11-23, Backlog 3a / 3c): laid out like Client Overview. A search box (title, description, requester), Filter and a **Sort** dropdown, then ONE table, New requests or Ready to announce, picked by the toolbar pills. Columns: chevron · Title (requester beneath) · Departments · Urgency · Importance · Requested on · Assigned to (the requester's pick on New requests, the assignee on Ready to announce). **Order:** both default to *Date added: Oldest* — `requested_on`, then id, undated imports last (`byAdded` / `sortRequests` in `backlogModel.js`; `created_at` is not used because the import stamped every row alike), so Ready to announce here ignores the board's drag order. The Sort dropdown also offers *Date added: Newest*, *Priority: Highest* (urgency + importance, ties to the older request) and *Title: A to Z*; a clicked column header overrides it for that list and choosing an option clears the header sorts. The sort, the list pick and the search are kept while switching tabs and reset when the page reopens. A row (or its chevron, or Enter) **drops its details open under it** instead of opening the drawer, and several can be open: the status line with the review right under it (Approve / Deny for a superadmin on a pending request, "Approved by …" on a ready one), then the Description, write-up, Move, Announcement and History cards side by side. Approve / Deny / Withdraw / Archive from a row show a green "where it went" line ("Approved: now on the Tasks board.", "Denied: moved to the Archive.", "Withdrawn.", "Archived."). A filter or lens that hides an open row closes it.
- **Archive** (`BacklogArchive.jsx`): announced AND denied requests, newest first, with a search (title, description, requester), a Show filter (Announced and denied / Announced / Denied) and its own department dropdown. Each row has an Announced or Denied pill. A superadmin gets **Restore** on an announced row (back to Ready to announce) and **Reopen** on a denied one (back to New requests). The page holds the Archive's department: opening the Archive with exactly one Department ticked in the Filter starts it on that department, and closing it with a department picked makes that the Filter's only Department tick (Requester and Assigned to ticks stay).
- **Card** (`BacklogCard.jsx`, Workbench style, the Tasks board only since the Requests tab became tables): the title, "requester · date", the department chips and the coloured **Urgency N** / **Importance N** pills (`ScorePill.jsx`: grey 1, blue 2, amber 3, orange 4, red 5; a dash when unset). Nothing else until it is opened: "Requested for: …" on a pending card with a pick, "Done by …" in Ready to announce, "Needs its write-up" on a Done card without one.
- **Drawer** (`BacklogDrawer.jsx`, Tasks board and Archive only): the blue header (where it is, the title, requester and date), then `BacklogDetails.jsx` stacked in one column: the description with its pills, the **What it does (for the announcement)** write-up, the review, Move to / Assign to selects for a superadmin (the touch-screen way to move a card), the announcement, and the history timeline. `BacklogDetails` is the same body a Requests row drops open (`layout="grid"`). The write-up shows only on an APPROVED request (the board, Ready to announce, the archive), never on a new, denied or withdrawn one (2026-11-23).
- **Phone** (asked for by Paxton 2026-11-23, although admin screens have no phone layout rule): below 640 px a Requests row is a card (title, requester and date, department chips, the two pills, who it is assigned to) and its details open inside the card as ruled sections without repeating the chips; the Move selects stack, in the drawer too. The Filter menu opens from the left there.
- **History:** the clean-up's rows (see *The sheet import*) read "Title replaced (imported title was cut off)", with "Was: <old title>" under it and "Title clean-up" as who did it; every other row names its admin, or "Sheet import".
- **Forms:** `NewRequestModal.jsx` (Title with a hint, "A short name for the change. Put the details in the description.", and an "n / 140" counter that turns amber from 120 characters and red at 140, where the box stops (2026-11-22, Backlog 6a); Department multi-select, Urgency and Importance 1–5, Description, and an optional, muted **Assign to** that only the requester sets while the request is pending), `DenyDialog.jsx` (a reason is required), `ArchiveDialog.jsx` (Announced on, today by default and never in the future, plus an optional note).
- **Departments:** `backlog/portalDepartments.js` (with the chip colours) and the backend's `constants/portal-departments.ts` are the same eleven names. Change both together.
- **Drag and drop** is native HTML5 (no library). A drag into another column lets the server place the card by priority; a drag up or down inside one column saves that position. The dragged card stays on the page, only hidden, so a drop outside every column (or Escape) ends the drag on it and it snaps back; until 2026-11-23 it was taken off the page, which lost that event and left it hidden until a reload.
- **Loading** (2026-11-20): while `portal_backlog_load` runs, the real Tasks / Requests pills show above `PortalBacklogSkeleton` (`shared/skeletons/admin.jsx`): on Requests only, the navy hero with its title and placeholder counts; then the toolbar, then the board (at the same 1280 / 768 px breakpoints, two lanes) or the Requests search row and one table (cards on a phone). The archive shows `PortalBacklogArchiveRowsSkeleton` while it loads. There is no "Loading…" text. A change to the board's layout changes its skeleton too.

## The rules (all enforced by the backend)

| Rule | Where |
|---|---|
| Title 1–140 characters, description 1–4000, at least one department from the list, urgency and importance whole numbers 1–5 | `validateFields` (`actions/portal-backlog/shared.ts`) + table checks |
| The requester and the date come from the session (`requested_on` is today in America/New_York) | `portal_request_create` |
| "Assign to" is only Jake, Paxton or no one; it is used once, at approval | `validateFields`, `portal_request_review` |
| Approve lands in the picked person's To do if they are still a superadmin, else in Approved but unassigned, placed by priority | `portal_request_review` |
| Deny needs a reason; a denied request leaves the board and the counts and shows in the archive | `portal_request_review`, `portal_backlog_load` / `portal_backlog_archive_load` |
| Only To do can be unassigned; a card in Ready to announce keeps its assignee | `portal_request_move` |
| A card enters Ready to announce only with a write-up, and one there cannot have it cleared (a task: optional) | `portal_request_move`, `portal_request_writeup_save` |
| A task: added by a superadmin only, born approved in a lane's To do (top), no urgency / importance, departments optional, an optional due date; never reviewed, withdrawn or unassigned; changed by a superadmin only | `portal_task_create`, `validateTaskFields` (`shared.ts`), `portal_request_review` / `_withdraw` / `_update` / `_move`, table checks `portal_requests_task_shape` / `_task_assigned` |
| Priority = urgency + importance, highest first; ties to the older request date, then the older id. Tasks sit above every request, in their own order | `priorityKey` (`shared.ts`), SQL `portal_backlog_resort` |
| Only a Ready to announce request is archived, with a valid date that is not in the future | `portal_request_archive` |
| A withdrawn request disappears from every view and count (the requester's own come back in `my_withdrawn`, unused by the page) | `portal_backlog_load` |

**One write path.** Every write goes through the SQL function `portal_request_apply(p_id, p_set, p_expect, p_events)`: the change and its history rows in one transaction, and `p_expect` is the state the handler decided on. If someone changed the request in between, it raises `portal_request_conflict` and the handler answers **409** ("This request changed while you were working on it. Reload and try again."), so two superadmins cannot both approve or both move a card.

## Bells (team notifications are bells only — TEAM_RULES §8)

Five `notifyByRule` rules, area **Portal Backlog**, kind `bell`, FYI, `dismissible`, pipeline `PORTAL_BACKLOG`, no `email_templates` rows. Each is sent with `forceRecipients`, so the Notification Editor can switch it off but not re-route it. The link is `/admin?tab=portal_backlog&request=<id>`: `AdminPortal.jsx` passes it to the panel. A pending or ready-to-announce request opens the Requests tab on its list with its row dropped open and scrolled into view (clearing a lens, filter or search that would hide it); a request on the board opens its drawer on the Tasks tab, and an archived one its drawer in the archive.

| Rule | To | Title | Message |
|---|---|---|---|
| `BACKLOG_new_request` | every superadmin except the requester | "<requester> submitted a portal request" | the title |
| `BACKLOG_approved` | the requester | "Your portal request was approved" | the title |
| `BACKLOG_denied` | the requester | "Your portal request was denied" | the reason |
| `BACKLOG_assigned` | the new assignee, when a card enters their lane (approval with them picked, or a move from Unassigned or the other lane), or a task is added straight into the other superadmin's lane | "<actor> assigned you a portal request", or "<actor> assigned you a task" for a task | the title |
| `BACKLOG_ready_to_announce` | the requester, when a REQUEST enters Ready to announce (never a task) | "Your portal request is ready to announce" | the title (+ "done by …") |

Never to the person who acted, and never to someone no longer in `allowed_admins` (re-read at send time: `bellAdmin` in `shared.ts`). Archive, restore, reorder, edits and write-ups send no bell. A failed bell is logged and never undoes the change. On the test site every bell goes to the tester with the `TEST - meant for:` line.

## The sheet import

`scripts/portal-backlog-sheet-import.sql` (edge repo — it holds staff names and request text, so it stays out of this public repo). Generated once from the sheet's CSV export: 89 rows, the 25 Approved / Completed rows skipped, 50 pending, 1 denied ("Denied in sheet"), and the 12 On Hold + 1 In Progress rows in Approved but unassigned in priority order (history note "Imported – was On Hold" / "– was In Progress"). The import first titled each row with the first eight words of the request + "...". On 2026-11-22 (Workbench *Backlog 6a*) `scripts/portal-backlog-title-fix.sql` (edge repo) replaced the 55 cut-off titles with short titles Paxton approved (run on the test site and on live 2026-11-22), keyed on `sheet_row` and only where the old title was still there; it writes one History row each, sends no bell and leaves descriptions alone. The import script now carries the approved titles, so a re-run cannot bring "..." back. Requesters are matched to `allowed_admins` by name. It writes the tables directly (no bells), keyed on `sheet_row`, so a second run adds nothing. Run on the test site 2026-11-17; run on live at release, after both migrations.
