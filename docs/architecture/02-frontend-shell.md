# Frontend shell

The frontend is a single Vite + React 18 + react-router-dom v6 SPA. No state library — each top-level page does its own load via [callApi](src/lib/api.js) and passes data down via props. There is **no React Context provider**, but [`src/lib/api.js`](src/lib/api.js) holds a small **module-level promise cache** for `load_data` and other read-only actions (anything matching `^load_|_load(_|$)`), so re-mounts within a session reuse the first response. Cache invalidates on `clearSession`.

**Loading UX**: each top-level page renders its real chrome (header, tabs, name, etc.) immediately and shows page-shaped placeholders in the content area until data lands — no "Loading…" text anywhere. Skeletons live in the [`src/components/shared/skeletons/`](src/components/shared/skeletons/index.js) package (rebuilt 2026-07-02): `primitives.jsx` (bars, cards, `HeroSkeleton`, `TableSkeleton`, `TokenFormSkeleton`, …) composed into per-page skeletons in `admin.jsx` / `tracks.jsx` / `portal.jsx`; `Skeleton.jsx` is a back-compat re-export barrel. List skeletons render 2–3 rows; all colors are `var(--vfo-*)` so they theme correctly in dark mode.

**Shared formatting + auth helpers (2026-09-22).** Three small modules were added so copies stop drifting. [`src/lib/dates.js`](src/lib/dates.js) `formatDate()` is the ONE display date formatter — **MM/DD/YYYY** — and 63 display sites across 20 files were converted to it from raw `split('T')[0]` / `slice(0, 10)`. It formats a `YYYY-MM-DD` prefix by string surgery, never through `new Date()`, which parses a date-only string as UTC midnight and renders the previous day west of Greenwich; that keeps the day byte-identical to what those sites printed before, so only the format moved. **It is deliberately NOT used for `<input type="date">` values, sort keys or comparisons** — those must stay ISO or they break, and the five files that already defined a local `formatDate()` rendering MM/DD (no year) for step dates import it aliased as `formatFullDate`. [`src/components/shared/LoginError.jsx`](src/components/shared/LoginError.jsx) renders the failed-sign-in message on all four portal login pages plus a static "you are on the <portal> portal, choose your portal" hint — shown to everyone, never looked up, because a lookup would leak whether an account exists (#355). [`src/components/shared/specialistDetails.js`](src/components/shared/specialistDetails.js) resolves a specialist's per-ecosystem Details & Benefits write-up for read-only surfaces, mirroring the admin editor's `entriesFor` fallback chain (array of `{ecosystem,...}` rows — keyed map — legacy flat `D&B_*` columns); the two must stay in step, since the editor is what writes those three shapes.

**Theming (2026-07-02)**: the app has a **light/dark mode**. `src/index.css` defines the semantic `--vfo-*` palette with a `[data-theme="dark"]` navy override; components use `var(--vfo-*)` in their inline styles (never raw palette hexes — gotcha #169). The preference lives in `localStorage.vfo_theme` and is applied as `data-theme` on `<html>` by [`src/lib/theme.js`](src/lib/theme.js): the portal-level pages (`AdminPortal`, `MemberPortal`, `ClientPortal`, `SpecialistPortal`, `TaxPlannerPortal` [added 2026-07-22], `ClientDetail`) call `usePortalTheme()` (applies on mount, resets to light on unmount), `main.jsx` calls `applyThemeForCurrentRoute()` at boot, and every portal's Settings renders the shared [`AppearanceCard`](src/components/shared/AppearanceCard.jsx) Light/Dark picker. **Login pages, the role picker, and all public token pages always render light.** The in-portal `MemberShowroom` follows the portal theme via a raw-hex dark palette (its CSS appends hex-alpha suffixes — gotcha #170); the website widget is unaffected.

**Error UX (2026-06-18, security remediation)**: the whole app is wrapped in [`src/components/ErrorBoundary.jsx`](src/components/ErrorBoundary.jsx) — a React class component (`getDerivedStateFromError` + `componentDidCatch`) mounted in [`src/main.jsx`](src/main.jsx) **outside** `<BrowserRouter>`. Any uncaught render/runtime error now shows a branded navy "Something went wrong" fallback card (inline styles, so it renders even if app CSS failed) with **Try again** (resets the boundary) + **Reload page** buttons, instead of the previous blank white screen. `main.jsx` also calls `Sentry.init({ dsn, environment:'production' })` at startup (error monitoring only — no Session Replay, no performance tracing) and `componentDidCatch` forwards the crash via `Sentry.captureException(error, { extra:{ componentStack } })`. See [../integrations/sentry.md](../integrations/sentry.md).

**Startup-failure banner (2026-08-20)**: a *rejected* bootstrap load is not a render crash, so the ErrorBoundary never sees it — `callApi` rejects, the shell's `catch` swallows it, and the portal used to render as a blank tab with nothing said. All four shells (`MemberPortal`, `AdminPortal`, `ClientPortal`, `SpecialistPortal`) now keep a `loadError` state alongside `loading`, set it in that `catch` (cleared at the top of every load so a re-run after a save doesn't leave a stale banner), and render a red "We couldn't load your portal" card above the tab body with the server's message and a refresh hint. The empty-state substitutes are **kept**, not replaced — the render paths below read the loaded shapes unguarded; the banner only says *why* they are empty. `TaxPlannerPortal` already had its own equivalent. Gotcha **#426**.

**Design system (2026-06-09 light-theme redesign)**: all styling is inline per file (no CSS framework); the only global styles live in [`src/index.css`](src/index.css) (page background, Inter font smoothing, slim scrollbars, button hover/active filters, input focus rings, `.vfo-skeleton` shimmer, `html{overflow-y:scroll}` to keep the layout from shifting when the scrollbar appears, and — added 2026-08-07 — the two-part `input[type="search"]` `appearance:none` reset (the element itself plus its `::-webkit-search-cancel-button` / `::-webkit-search-decoration` pseudo-elements) that makes a `type="search"` box render identically to `type="text"`, so search inputs can be reclassified for Chrome-autofill suppression at zero visual cost, gotcha #343). Two shared chrome components were added: [`src/components/shared/VfoWordmark.jsx`](src/components/shared/VfoWordmark.jsx) (the VFO wordmark, `light` prop for the navy-gradient portal headers) and [`src/components/shared/AuthShell.jsx`](src/components/shared/AuthShell.jsx) (the split-screen layout wrapping all login/setup pages). Conventions: ink `#16264a` body text, navy `#002973` headings, primary `#125ecc`, white radius-16 shadowed cards, tinted `#eef2f9` inset panels, status colors only in bullet dots + pills.

**Per-step email previews (2026-07-20)**: [`src/components/shared/StepEmailsChip.jsx`](src/components/shared/StepEmailsChip.jsx) renders a tiny "Emails (N)" pill next to an email-sending step label; clicking it opens a centered modal previewing every template that step can send — live subject/body, To/Cc/Bcc resolved via `ROLE_LABELS`, variant + member-behalf twin rows, with known values filled from a `context` prop and unknown tokens shown as bracketed `[Token]` chips. It lazy-loads via `loadCachedAction('load_email_previews', {pipeline})` with a silent fallback to `automation_load_email_templates`, and is `!readOnly`-guarded on member-visible tracks. [`src/components/shared/templateMeta.js`](src/components/shared/templateMeta.js) holds `mv` / `TEMPLATE_META` / `ROLE_LABELS` — **moved verbatim out of `EmailTemplatesPanel.jsx`** (which now imports them) so both the panel and the chip share one source. Mounted across 9 admin surfaces (MAP 1 / Tax / Regular / PIP / PFT tracks + Advisor/Accountant/Specialist onboarding + the Membership Fees panel). See gotcha #248.

**Vault "Request documentation" button (2026-07-30)**: [`src/components/shared/RequestDocsButton.jsx`](src/components/shared/RequestDocsButton.jsx) is a self-contained admin control that drops into any vault section — a small "Request documentation" pill that opens an **inline compose card mirroring the seeded `VAULT_request_documentation` email byte-for-byte**, with the textarea sitting exactly where the admin's typed text lands in the template and a disabled preview of the "Upload Documents" button. Send posts `vault_request_docs` and shows a transient "Request email drafted" confirmation (8s). It is wired in by an optional per-section `requestDocs {entityType, entityKey, recipientName, recipientFirst}` prop on [`VaultSections.jsx`](src/components/shared/VaultSections.jsx) — sections that omit it are unchanged — passed by [`MemberVault`](src/components/shared/MemberVault.jsx) and [`SpecialistAdminVault`](src/components/admin/SpecialistAdminVault.jsx) **only when `admin===true`** (so the member and specialist self-portals never render it) and, on its own copy of the section list, by [`ClientVaultTab`](src/components/admin/ClientVaultTab.jsx) when `sec.canManage && !readOnly` (so the client Sensitive section inherits the `isTaxAdmin` `canView` gate and a tax planner's read-only view hides it). The ERT/VFOS third section never gets one. Six placements total; see gotcha #310.

**Admin search inputs (2026-08-07)**: every free-text search box on an admin/portal surface carries **`type="search" name="search" autoComplete="off"`** (React casing — `autoComplete`), and its **placeholder must not contain loyalty-card trigger words** ("member number", "member #", "membership"). Chrome's Google-Wallet loyalty autofill classifies fields by regex over placeholder/label text and **ignores `autocomplete="off"`**, so it would otherwise render a "Manage loyalty cards…" dropdown on top of the search results — the attributes alone were shipped first and did **not** fix it. 19 inputs across 14 files follow this (`MembersPanel` x5, `MembershipFeesPanel` x2, plus `MemberOverviewPanel`, `ClientOverviewPanel`, `SpecialistsPanel`, `TaxPlannersPanel`, `SpecialistPaymentInput`, `MSMTracking`, `NewModelSaleModal`, `PlannerClientsList`, `MemberCIQ`, `MemberWebsitePlugin`, `MemberShowroom`, `MemberPortal`). Audit with `placeholder="[^"]*[Mm]ember` across `src` — only `<textarea>`s and non-DOM `placeholder` props may legitimately match. The `index.css` search-decoration reset above keeps the reclassification invisible. Gotcha **#343**.

**Credential forms — autofill identity is mandatory (2026-08-10)**: every login, set-password and change-password form carries **`id` + `name` + `autoComplete`** on its fields (`username` on the email box, `current-password` on a login passcode, `new-password` on a chosen one), sits inside a real `<form>` with a `type="submit"` button, and reads **`state || ref.current?.value`** on submit. Without the field identity a password manager can save an entry but can **never recognise the field again to offer an update**, so it keeps re-filling a passcode the user already replaced — which, plus the 5-failures-per-15-minutes login throttle, is a hard lockout that looks exactly like a broken backend (gotcha **#354**). The `useRef` fallback exists because an extension may set `.value` directly without dispatching a React-visible event, leaving `useState` empty and posting a blank field. Covered: the five login pages (`AdminLogin`, `ClientLogin`, `MemberLogin`, `SpecialistLogin`, `TaxPlannerLogin` — each also stores **the email that actually authenticated** in `setSession`, not the state variable), [`SetPasswordPage.jsx`](src/pages/SetPasswordPage.jsx), [`ForgotPasswordPage.jsx`](src/pages/ForgotPasswordPage.jsx) and [`ChangePasswordCard.jsx`](src/components/shared/ChangePasswordCard.jsx) — the last of which changed from a `div` to a `form` and carries a **clip-hidden `readOnly` username input** (`hiddenFieldStyle`) holding `getSession()?.email`, because a change-password form with no username field is un-updatable for the same reason. This is the *opposite* problem to the search inputs above (#343): there we are suppressing an autofill classifier, here we are feeding one.

**Person-name profile links (2026-08-03)**: [`src/components/shared/personLinks.jsx`](src/components/shared/personLinks.jsx) exports **`MemberNameLink({memberNumber, children, style})`** and **`ClientNameLink({clientId, program, tab, children, style})`** — the sanctioned way to render a clickable person name on any **admin** surface — and, since 2026-09-14, `MemberNameLink` is **portal-aware**: under `/tax-planner` it goes to `/tax-planner/member/:memberNumber` instead of `/admin` (a planner session cannot load `/admin`, #494). `ClientNameLink` navigates to `/admin/client/<id>` (+ optional `?program=`/`&tab=`); `MemberNameLink` reuses the **existing** `/admin?member=<member_number>&_n=<Date.now()>` deep link (AdminPortal String-coerces the match against `plugin_member_number`), so **no `onOpenMember` prop threading is needed** and #193's nested-prop trap is sidestepped — the `_n` cache-buster is stamped inside the onClick because AdminPortal reads `window.location.search`. Both render a `var(--vfo-primary)` span with the `PaymentsTable` hover-underline idiom and **`stopPropagation()`** (safe inside expandable/clickable rows); a **falsy id degrades to a plain `<span>`**. Contract: `baseStyle` spreads **after** the passed `style`, so a passed `color` is dead — pass only `fontSize`/`fontWeight`. Mounted across 23 admin surfaces (client overview + detail header, advisor/accountant onboarding list rows, member onboarding, membership fees, outstanding links, member KPI, tax planners, the three revenue + three reconciliation panels, growth credits accounting + redemptions, all four automation panels). **Never used in the member/client/specialist/planner self-portals** (an `/admin…` destination bounces a non-admin to login), and `TrackHero` titles get an "Open member profile →" `meta` link instead of a wrapped heading. See gotcha #322.

**Direct pill (2026-09-18)**: [`src/components/shared/DirectPill.jsx`](src/components/shared/DirectPill.jsx) is the ONE marker for a DIRECT tax case (`client_tax_plans.tax_route = 'direct'` — the member runs the case and is its Planning Facilitator, `clients.pf_member_number`). Orange on purpose so it never reads as a status or a program; `size='sm'|'md'`; rendered wherever a plan or client is listed — the member and admin client lists, the Client Overview "Tax Planning - Direct" row, the tax plan hero, the intake step-1 chooser. Owner chips on the tax step rows are a different thing (see [../flows/tax-planning.md](../flows/tax-planning.md)).

Built and deployed as a static site to GitHub Pages at `https://vfoportal.com/` (per [package.json:9](package.json) — `gh-pages -d dist`).

**Not routes — static files served directly (added 2026-07-28, gotcha #295).** `/privacy.html` and `/terms.html` are real files in `public/`, NOT entries in this table and NOT React pages. GH Pages has no SPA rewrite, so an unknown path returns a genuine HTTP 404 and serves `public/404.html` (which stashes the path in `sessionStorage` and redirects to `/`) — a crawler or security-vendor reputation scanner would see the 404 or an empty shell. Public documents that exist to be read by machines therefore must be static files with inline `<style>`, and are linked with a plain `<a href>` rather than a router `<Link>`. The same rule covers `public/robots.txt` (a `Disallow:` per sensitive top-level route prefix), `public/sitemap.xml` (a `<url>` per public page) and `public/.well-known/security.txt`. **Adding a new sensitive route above means adding its prefix to `robots.txt`; adding a new public page means adding it to `sitemap.xml`.**

**`/store/` — "The VFO Library", a standalone 3D page rather than a route (added 2026-08-09).** `public/store/` is a self-contained static application: `index.html` plus six plain browser ES modules (`main.js`, `data.js`, `covers.js`, `list.js`, `textures.js`, `props.js`) and a vendored `vendor/three-0.160.1.module.min.js`. It renders a walkable 3D bookstore in which every public VFO specialist is a hardcover book (front cover = headshot + name + tagline, flip for the bio, a DOM panel for the full profile), with an accessible 2D list fallback for anyone who cannot or does not want to use the 3D view. It is **entirely outside the React app** — no entry in the routes table above, no file in `src/`, no router involvement, no shared components and no shared CSS. `vite build` copies the directory **verbatim** (no bundling, no asset hashing), and because it is a real directory carrying its own `index.html`, GitHub Pages serves `/store/` as a genuine 200: it therefore needs **no `scripts/emit-route-pages.mjs` entry**, and `store` is deliberately absent from that script's `ROUTES` list so nothing can overwrite the page's own `index.html`.

Data comes from **PostgREST directly with the public anon key — the page never calls `vfo-admin-api`.** `public/store/data.js` mirrors the embeddable widget rule-for-rule: the anon 8-column `experts` select plus the same three exclusions (non-`Active`, `Member Services` members, `vfo_accredited`), so `/store/` exposes nothing the widget did not already expose — see gotchas #201 / #231 and **#345**, which makes this the *third* public consumer of that surface. three.js is **vendored rather than an npm dependency**, and the page's importmap names the exact vendored filename, so the two move in lockstep (**#348**). Rendering is **pixel-budget-based per detected GPU tier** rather than native-resolution (**#347**), and `?debug=1` prints the GPU string, which is the first thing to check on any "it stutters" report (**#346**).

## Accounting share columns — how a dollar picks its column (2026-08-24)

The Accounting tab's `AccountingCombinedPanel.jsx` groups — VFO Specialist Revenue · Holistic Planning · Tax Planning · Additional PIP, each Revenue + Reconciliation, and since 2026-08-24 **VFO Specialist License Fees**, which wraps three pills: License Fees · **License Reconciliation** (`SpecialistLicenseReconciliationPanel.jsx`, NEW — all-time per-specialist aggregate, no year filter by design) · **Outstanding Payment Links** (`SpecialistLicenseOutstandingPanel.jsx`, NEW — reuses `OutstandingLinksPanel`'s exported internals, read-only, no resend), and since 2026-09-23 **VFO Specialist Background Checks** (`maxWidth` 900px), the same three-pill shape: the monthly received-payments ledger with the send-request form (`SpecialistBgPanel.jsx`) · **Background Check Reconciliation** (`SpecialistBgReconciliationPanel.jsx`) · **Outstanding Payment Links** (`SpecialistBgOutstandingPanel.jsx`), all reading `specialist_bg_payments_load` through `bgRowsFrom` ([../flows/specialist-bg-requests.md](../flows/specialist-bg-requests.md)) — print every slice of a split as a plain dollar figure. **[`src/components/admin/shareLegState.jsx`](src/components/admin/shareLegState.jsx) is the single frontend source of truth** for what that figure MEANS — it turns a leg's payout column into a `{note, tone}`, dims unpaid money, and supplies the aggregate sub-notes. Full rules and the whole note vocabulary live in **gotcha #395**; two things belong here because they are structural rather than cosmetic:

- **`isMoneyMappingLeg(state, decision)` decides which of the two member columns a slice lands in** — Member Revenue Share or Member Money Mapping. A **settled** leg is filed by **what happened to it** (its own note: `paid` → Revenue Share, `money mapping` → Money Mapping); only an **unsettled** leg (blank / in progress / held / awaiting / failed) falls back to the member's current `members.revenue_decision`. **These columns are history, not a restatement of a member's current preference** — cash that really moved stays under Revenue Share even after that member switches to Money Mapping. It matches on the NOTE, not the raw column, so MAP 1 / Tax (`legState`) and PIP (`pipShared`'s `pipMemberState`) — which store different vocabularies — need no per-track variant. Wired into all six Holistic / Tax / PIP revenue + reconciliation panels.
- **Aggregate cells carry TWO sub-notes that PARTITION the owed money:** `PendingNote` (`$X pending`) for ordinarily-owed money and `HeldNote` (`$X held - suspended` / `- paused`) for money parked behind a suspended or paused member. A held dollar is never counted under both.

The SpecRev pair is the exception that does not use `shareLegState`: **[`specialistRevenueShared.jsx`](src/components/admin/specialistRevenueShared.jsx)** owns its own `lineStatusMeta` pills over `specialist_revenue_lines.payout_status` (a **snake_case** family — `held_member_suspended` / `held_member_paused` — not the Title-Case `rev_paid` vocabulary), plus `memberShareNote` annotations on the member-dollar cells (which carried **no** paid note at all before 2026-08-24) and a **"By member"** view. **No-money deal records (2026-09-23):** `+ New Payment`'s fourth option in `SpecialistPaymentInput.jsx`, *"Record deals — no payment"* (`payment_method:'none'`), locks every $ input and needs only a recipient + deals ≥ 1 per line; the saved request (`payment_status='recorded'`) shows a green **"Deals Recorded"** chip (`REQ_STATUS.recorded`), its `no_payout_due` lines read as settled, it counts in the period totals + By-member rollup alongside `received` (adding deals and $0), `SpecialistRevenueAutomationPanel` shows *"nothing to pay out"* for it, and `isNoMoneyRecord()` makes it deletable (*"Delete record"*). `SpecialistRevenueAutomationPanel`'s `OPEN_PAYOUT` and `SpecialistReconciliationPanel`'s `PENDING_PAYOUT` sets must both admit every non-terminal status or a held line renders as settled (#433).

## Login-error handling in `callApi` (2026-06-18)

[`src/lib/api.js`](src/lib/api.js) treats a `401` differently depending on the action. A `401` on a **login** action — `LOGIN_ACTIONS = ['admin_login','member_login','client_login','specialist_login','login']` — means *bad credentials*, so `callApi` **throws the server error inline** (`data.error || 'Invalid credentials'`) and the login page renders it; it does NOT clear the session or redirect. A `401` on any **non-login** action is still treated as an expired session: `clearSession()` + hard redirect to `/` (unchanged). Previously every `401` hit the redirect path, which bounced a failed login straight off the login screen; this is also what lets the H1 rate-limit `429`/`401` "Too many login attempts" message surface on the login form. See [04-auth-and-sessions.md](04-auth-and-sessions.md#401-auto-redirect).
